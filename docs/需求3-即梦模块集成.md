## 1. 背景与目的

`aigen-panel` 当前是一个多用户 AI 生成面板，主线为三阶段流水线（P1 生成形象 / P2 获取灵感 / P3 视频生成），后端 NestJS 10 + Prisma 5 + PostgreSQL，前端 React18 + Vite + Antd5，Cookie-JWT 鉴权。
其 `ai-channels` 模块复用了 `jimen2api` 的「Bearer 拆分 + 随机选号」思路，但只覆盖了「OpenAI/Anthropic 兼容渠道」，并没有把即梦（Jimeng）自身的图像/视频/数字人能力接进来。

`jimen2api-all-master`（源码名 `jimeng-free-api`）是一个 **Koa** 服务（better-sqlite3 + cron），包装字节跳动 **即梦 (Jimeng)** AI，提供：
- 即梦图像生成、视频生成（OpenAI 兼容 `/v1/images`、`/v1/videos`）
- 对话补全 `/v1/chat/completions`（支持流式）
- 国内数字人（图片+音频→唇形同步视频，`/v1/digital-human-cn`）
- 模型列表、token 存活/积分检测
- 内置可视化管理控制台 `/dashboard/*`

**目标**：把上述即梦能力与接口，作为 aigen-panel 的一个**新功能模块**集成进来，使面板用户也能用即梦生成图像/视频/数字人。

## 2. 两个必须严格区分的概念（用户明确强调）

| 概念 | 含义 | 数据来源 |
|------|------|----------|
| **A. 号池功能 = 本地导入 cookie** | 管理员在 aigen-panel **本地**导入即梦的 `sessionid`/Cookie，存入本地账号池；生成时从池中随机/轮换选取账号 | aigen-panel 自身数据库（新增表） |
| **B. 外部号池服务 `http://43.130.31.50:18813`** | 一个**独立**的号池 SERVICE，aigen-panel 作为**客户端**去调它、从它拉取/租借即梦账号 | 外部 HTTP 服务（契约待探明） |

**关键说明**：
- `jimen2api-all-master` 的源码**不引用** `:18813`；它的「号池」是调用方在每次请求的 `Authorization: Bearer t1,t2,t3`（逗号分隔，随机选一个）里塞 token，**不在服务端持久化**。
- 我们要做的「A」是把这种「多 token 池」**持久化到本地**（管理员导入、存库、随机选号）。
- 「B」是**另一条账号来源**（外部服务连接器），与 A 是平行的两种「账号供给方式」，选号逻辑可共用，但**绝不可混为一谈**：A 是「我自己导入的号」，B 是「向外部服务借的号」。
- 待执行阶段第一项，必须先探明 `:18813` 的接口契约（见 §8 开放问题）。

**即梦请求核心技术点（需原样移植）**：
- `generateCookie(refreshToken)`：用 `sessionid`/`sid_tt` 等拼即梦 Cookie。
- `request()`：计算 `Sign`（`md5`）、`Device-Time`，注入伪装 UA/Referer，访问 `https://jimeng.jianying.com...`。
- AWS SigV4 上传：图片走 `imagex`、音频走 `vod`（含 `ApplyImageUpload`/`CommitImageUpload`/`ApplyUploadInner`/`CommitUploadInner`），逻辑较复杂。
- 错误码映射：积分不足 `ret=5000/1006` 抛专用异常。

## 4. aigen-panel 现状与集成点

- **鉴权**：Cookie-JWT（`auth/jwt.strategy.ts`），控制器 `@UseGuards(JwtAuthGuard)`。
- **模块化范式**：每模块 `*.controller.ts` / `*.service.ts` / `*.module.ts` / `dto/*.dto.ts`，`@Controller('api/xxx')` 前缀。
- **加密**：现有 `encrypt/decrypt` 工具，`ai-channels` 用 `apiKeyEnc` 存密文、返回时 `keyMask` 脱敏——**新账号池的 Cookie 必须复用同一套加密/脱敏**。
- **共享库约定**（见项目记忆）：歌曲/形象/提示词/渠道均为**全站共享**，非按用户隔离。即梦账号池也应是**管理员级共享资源**。
- **出站安全**：`EgressGuard` 按 `ALLOWED_EGRESS_HOSTS` 白名单放行（SSRF 防护）。即梦域名 `jimeng.jianying.com`、`*.bytedanceapi.com`、`imagex.bytedanceapi.com`、`vod.bytedanceapi.com` 需加入白名单。
- **并发控制**：`configuration.ts` 已有 `redisUrl`，可复用做选号 Redis 锁（参考 `ruoyi-pool-center` 的选号锁思路）。
- **前端**：`App.tsx` 13 个页面，侧边栏（`AppLayout.tsx`）加菜单即可；现有 `AiChannels.tsx` 是「管理员配置渠道」的 UI 范本，新账号池页面可沿用其范式。

### 5.2.x Cookie 调用策略（关键修正，实测结论）

> ⚠️ 重要：整份 cookie map **必须保存**（用于兜底查值），但**调用即梦时不能直接原样回放全部字段**——实测原样回放会**登录失败**。正确路径如下：

1. **存储**：导入时把整份 cookie map JSON 加密存入 `cookieEnc`；同时提取 `sessionid`（=`sid_tt`=`sessionid_ss`）单独存字段，并从该条目的 `expirationDate` 解析出 `expireAt`。
2. **主调用路径（正常可用）**：沿用 jimen2api 的 `generateCookie(refreshToken)` 逻辑——**只用 `sessionid` 值重建 cookie**（填 `sessionid`/`sid_tt`/`sessionid_ss`，并现生成 `sid_guard` 时间戳），不回放其余字段。这是能成功登录的唯一稳定路径。
3. **兜底路径（登录失败时）**：当主路径请求返回鉴权失败/会话失效（`ret` 指示 session 无效、被踢、或 `check` 存活失败）时，**再从 `cookieEnc` 的 map 里找对应字段**（`uid_tt`/`ttwid`/`odin_tt`/`session_tlb_tag`/`sid_ucp_v1`/`sid_guard` 真实值等）注入/修补 cookie 后重试，作为自愈手段。
4. **自愈仍失败**：标记 `status=expired`，提示管理员重新导出导入（cookie 已真正过期，map 内的 `sessionid` 同样失效，无法凭旧 map 复活）。

> 设计要点：map 是「保险箱」而非「直接回放源」；`sessionid` 字段是高频热路径用的轻量句柄；`cookieEnc` 是异常时的修复原料与审计留存。

## 6. 关键技术点与风险

1. **即梦协议原样移植**：Cookie 构造、`Sign`/`Device-Time` 计算、AWS SigV4 图片/音频上传——逻辑复杂，需完整搬运 `core.ts`，建议先写单测验证签名。
2. **流式响应**：chat/数字人流式在 NestJS 需用 `@Res() res` + `PassThrough` 透传，且**绕过**现有的 `{code,message,data}` 响应拦截器（否则 SSE 被包装破坏）。
3. **选号与并发**：多请求同时选同一账号 → 参考 `ruoyi-pool-center` 用 `redisUrl` 加 Redis 锁；账号过期/掉线要自动标记 `expired` 并轮换。
4. **SSRF 防护**：即梦相关域名必须加入 `ALLOWED_EGRESS_HOSTS` 白名单（出站受信）。
5. **加密存储**：Cookie 复用现有 `encrypt/decrypt`，返回脱敏，绝不回明文。
6. **大文件/超时**：即梦上传图片/音频超时分别达 45s/60s/120s，需调高 axios 超时与网关 body 限制（参考现有 `MAX_INLINE_IMAGE_KB`）。
7. **多用户隔离**：生成任务归属 `userId`；账号池为管理员共享（沿用 ai-channels 约定）。
